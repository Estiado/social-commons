# 微信链接提取排查 · 2026-10-23

用户要求重新核对最早Netlify版本的微信提取能力。本轮未为未知效果添加代理、切换服务器或绕过验证。

## 已核对的差异

- 最早 `dddbe34` 的 `netlify/functions/extract-article.ts` 使用普通HTTP fetch，带Chrome/120 User-Agent和语言请求头，再用Cheerio读取常见容器或所有p段落；没有浏览器渲染、登录态或验证码处理。
- 旧版会先按URL查articles缓存；命中就返回已有ID，并不再次抓取。后来的 `2e0b551` 明确返回cached标识。因此“旧版成功”可能来自当时来源响应不同或缓存命中，不能仅从提交历史确定是哪种原因。
- 现 `server/articleFetch.ts` 保留超时、体积限制和每跳URL校验，未带旧User-Agent。恢复旧请求头值得做对照，但不是已证实的修复。

## 下一条可落地的路径

对正常返回正文的链接，继续使用来源容器解析；返回验证页面时，服务端没有可供解析的全文。若读者在自己的浏览器或微信中正常打开了文章，可以另外设计“从当前可读页面采集”的入口，再复用现有结构化阅读模型。它需要用户侧浏览器操作/采集工具，移动端支持要单独验收；不应承诺只粘一个链接就一定成功。

先拿一条当年确实成功的原文链接与当前同一链接对照，并在用户正常浏览器中核对可见正文；不要复制用户Cookie到服务器、采集登录凭证或自动处理验证码。来源站不返回正文时保留明确失败状态，不把验证提示或两段摘要当全文。
